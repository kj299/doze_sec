# benign_corpus.txt -- known-BENIGN artifacts that look like attacks.
#
# Read by tools/benign_corpus_check.ps1. Every entry is a false-positive
# twin: something a real machine carries that resembles an indicator, and
# that the audit must report as context (OK/INFO), or as a finding a person
# can adjudicate with the note below. Two of these fired as ACTIVE COMPROMISE
# on the owner's own machine in 2026-08 (P9NP, Event 104) because they had
# never been tested; a third (never-onboarded Sense) contradicted its own
# summary. For this audience a false "you are compromised" is the most
# harmful output the tool can produce.
#
# FORMAT -- INI-style blocks (regex-safe; the '|' corpora cannot hold regexes):
#   [id]                    short slug, unique
#   class     = QUIET       the tool prints a CONTEXT line for the benign twin;
#                           every report line matching `signature` must carry
#                           a leading tag <= maxsev (OK < INFO < WARNING < CRITICAL).
#                           -Mode Report FAILS on a higher tag.
#             = ADVISE      `signature` is the FINDING-shaped line that has a
#                           known benign cause; on a real machine a match prints
#                           the note (how to verify). The human adjudicates;
#                           never a failure.
#   maxsev    = OK|INFO|WARNING   (QUIET only)
#   proof     = harness:<Name substring of an Invert=$true case in tests/detection_selftest.ps1>
#             | ci:<step-name substring in .github/workflows/windows-smoke.yml>
#             | field:<why this cannot be planted -- observable only on a real machine>
#             several proofs: separate with ';'
#   signature = .NET regex matched per report line
#   note      = origin, and how a person verifies it on their machine
#
# -Mode Lint fails on: an entry without class/proof/signature/note, an
# unresolvable proof, an invalid regex, a harness Invert case that no entry
# catalogues (every false-positive guard must be documented here), or fewer
# than 10 entries (vacuous). -Mode Report is run by tests/field_test.ps1 on a
# real machine and by the harness on its own report.

# ---- QUIET: the audit prints context, and must keep it at or below maxsev ----

[office-c2r-virtual-modules]
class     = QUIET
maxsev    = INFO
proof     = ci:module_inspect.ps1 -SelfTest; field:a CI runner has no Office installation, so the real Click-to-Run layout can only be observed on a machine with Word or Excel running
signature = runs from a virtualized package \(Office Click-to-Run / MSIX\)
note      = Office Click-to-Run executes in a virtual application environment with PRIVATE COPIES of its files under <install>\root\VFS\ProgramFilesCommonX64\, so WINWORD reports a C:\Program Files\Common Files\Microsoft Shared\Office16\ path that does not exist outside the process. Field false positive 2026-09-06: the first audit run with Word open produced FOURTEEN "[WARNING] ... reflective or unbacked load ... (T1055)" lines for ordinary Office and VBA DLLs. Fixed by resolving through the VFS before declaring a module absent. Verify: (Get-ItemProperty 'HKLM:\SOFTWARE\Microsoft\Office\ClickToRun').InstallPath, then dir "<that path>\root\VFS\ProgramFilesCommonX64\Microsoft Shared\Office16\mso.dll".

[com-clsid-stale-updater]
class     = QUIET
maxsev    = INFO
proof     = ci:com_clsid_check.ps1 -SelfTest
signature = point at a file that is not present -- they cannot load as-is
note      = Brave's updater (Omaha, as used by Chrome and Edge) registers HKCU CLSIDs pointing into a versioned directory and leaves the registration behind when it rolls to a new version. Field false positive 2026-09-06: three CLSIDs -> ...\BraveSoftware\Update\1.3.361.151\psuser_64.dll raised '[WARNING] Suspicious COM CLSID overrides (3)' on a clean machine. The check already had a vendor tier, but it keys on the Authenticode SIGNER and a missing file has none. A registration whose file is absent cannot load anything; it stays a WARNING only when the path is a staging directory. Verify: Get-ItemProperty 'HKCU:\Software\Classes\CLSID\<guid>\InprocServer32' and Test-Path the value.

[hosts-docker-desktop]
class     = QUIET
maxsev    = INFO
proof     = ci:hosts_check.ps1 -SelfTest
signature = map a local-only name or point at loopback
note      = Docker Desktop writes host.docker.internal, gateway.docker.internal and kubernetes.docker.internal into HOSTS on every machine it is installed on; WSL, VirtualBox and Lando do the same. Field false positive 2026-09-06: these raised '[WARNING] Non-standard entries found in HOSTS file. Review for DNS hijacking.' The check now grades an entry by what it DOES, not by the address alone. Verify: type %SystemRoot%\System32\drivers\etc\hosts -- a private or loopback address mapped to a .internal/.local/.test name is dev tooling.

[module-not-visible-system-path]
class     = ADVISE
proof     = ci:module_inspect.ps1 -SelfTest
signature = mapped into the process but not visible on disk at that path
note      = This is the honest half of the Office Click-to-Run fix: the module claims a Program Files or Windows path, the virtual file system did not resolve it, and the loading process was not identifiable as a virtualized package. Two causes look identical from outside -- app virtualization the tool could not resolve (Click-to-Run key unreadable, an unusual package layout), or a module whose file was deleted after loading. It is deliberately NOT asserted to be an injection. Verify: (Get-Process <name>).Path, then check whether an ancestor of that path has a VFS subdirectory; if it does, this is virtualization.

[edr-name-service-install-residue]
class     = ADVISE
proof     = field:the residue is an Event 7045 record, which no cleanup can remove; a CI runner is discarded instead
signature = Suspicious service installations found
note      = A service installed with a cmd.exe/powershell/rundll32 image path is exactly an attacker's shape, and the check is RIGHT to flag it -- including when the service is named after a real EDR product. Observed on the owner's machine 2026-09-06: six 7045 records for 'SentinelAgent' left by a manual run of the CI EDR verification block on 2026-08-30. Cleanup deletes the service; it cannot delete the log record. The service NAME is deliberately not excluded -- an attacker would then hide a service by calling it SentinelAgent. Since #200 the harness plants carry 'dz_selftest' in the image path, which the check already excludes and reports as a count. Verify the TimeCreated of each record against when you last ran tests\manual_ci.ps1 or a CI paste block; an install you cannot account for is a real finding.

[hosts-blackhole-security-domain]
class     = ADVISE
proof     = ci:hosts_check.ps1 -SelfTest
signature = make a SECURITY or UPDATE domain unreachable
note      = A HOSTS entry pointing windowsupdate, Defender or an AV vendor at loopback or 0.0.0.0 stops that product updating -- standard defence evasion (T1562.001). This was INVISIBLE before 2026-09-06: the old findstr pipeline dropped every line containing '127.0.0.1', which is exactly how blackholing is written. A privacy/ad-blocking HOSTS list can also carry telemetry domains, so adjudicate: an entry you or a list you installed added is benign; one you cannot account for is not. Verify each named domain resolves normally after commenting the line out.
